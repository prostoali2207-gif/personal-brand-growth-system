## Core principle

Do not make "the service" the topic when a buyer problem, professional decision, real artifact or real process can carry the content instead.

The service should become obvious from the work.

## Preferred mechanisms

### REAL WORK / DEMONSTRATION
recognizable business situation -> real action/artifact -> observable next state -> short judgment

### PROFESSIONAL DIAGNOSIS
default approach -> exact weakness -> why it matters -> proof -> what Ali chose instead

Do not invent a common mistake or business harm without evidence.

### LIVE CRITIQUE / TEARDOWN
artifact on screen -> one question -> visible critique -> concrete decision/change

### BUILD / FAILURE / REPAIR
goal -> attempt -> failure -> diagnosis -> repair -> verified state

### CONTRAST
surface A vs surface B -> one meaningful difference -> business meaning

No fake before/after performance.

### BEHIND THE SCENES / OPERATOR
actual work session -> decisions -> artifacts -> constraints -> what changed

Competence should be observable without saying "I am an expert."

## Hook families to test

Prefer:
- specific buyer question;
- visible mistake/problem;
- earned professional disagreement;
- real experiment;
- concrete constraint;
- artifact critique;
- "I changed X because Y" when authorship evidence permits.

Avoid as default:
- "Сегодня расскажу...";
- "Я делаю сайты...";
- flat service lists;
- generic "3 tips";
- abstract AI copy;
- technical term first;
- fake pain such as "you are losing leads" without evidence.

## Evidence order

buyer meaning -> observable proof -> implementation depth only if useful.

Not:
technology -> architecture -> buyer meaning at the end.

## Selling rule

Earn the inference:
"this person can solve this type of problem"
before saying:
"hire me."

Exact CTA remains an upstream commercial decision.

## Distinctiveness rule

Every candidate should contain at least one earned judgment:
- what Ali prioritizes;
- rejects;
- changed;
- noticed;
- why one option was chosen.

If removing project nouns leaves generic agency copy that anyone could say, revise.

## Proof rule

Prefer:
- real screens;
- real workflow;
- real implementation state;
- real decision artifact;
- real failure/fix.

Avoid fake dashboards, generic stock animation and code montage as substitute for proof.

## Audience guard

Primary viewer = ordinary business owner/manager, not developer.

Test:
Can they understand why this matters before hearing backend/API/agent terminology?

If no, reframe or move technical depth later.

## Reference-use rule

1. state mechanism;
2. strip creator-specific expression;
3. rebuild from Ali's verified evidence;
4. compare derivative risk;
5. discard if it only works because of the reference's persona.

## Production implication

Do not assume high-polish production is required.

Benchmark supports testing:
- screen + voice;
- real artifact walkthrough;
- talking head where useful;
- live critique;
- low-edit operator footage;

when concept/proof is strong.

Capture/edit choices remain with their owner cores.

## PARTS-FLOW-01

Do not resume the polite explainer.

Run fresh divergence across:
- real demo;
- diagnosis;
- live critique;
- contrast.

Select against:
buyer relevance, evidence safety, authorial judgment, distinctiveness, proof visibility and commercial continuity.
