## VERDICT

**MULTI-PROJECT LAUNCH ASSET IS STRUCTURALLY VIABLE**, but only if the projects function as proof of one recurring system pattern.

A three-item services/portfolio list is rejected.

## COMMUNICATION_JOB

Establish the account's professional category by making one common work pattern legible across materially different verified artifacts.

The viewer should leave with:
`different surfaces -> same systems-building logic`.

## ATTENTION_CONTRACT

Opening job:
introduce a business/system distinction broad enough to apply to all three proof families, without naming the services list or leading with FleetDesk.

The opening must create the question:
**what makes a visible digital artifact part of a working business system rather than an isolated screen/tool?**

Payoff obligation:
the asset must answer using real transitions/relationships from multiple projects, not a generic definition.

## INFORMATION_ORDER

### B1 — COMMON PROBLEM / SYSTEM PRINCIPLE
Job:
establish one transferable systems question.

Do not:
list "sites / CRM / automation / AI".

### B2 — PROOF 1: ENTRYPOINT -> OPERATION
Source:
auto-parts landing + BayerCRM.

Show:
a visible request starts on the landing and continues through the implemented request pipeline into BayerCRM.

Purpose:
demonstrate that a landing can be one surface inside a larger operating flow.

### B3 — PROOF 2: BUSINESS RULE -> STATE CHANGE
Source:
FleetDesk.

Show:
one compact verified contract/vehicle state relationship.

Purpose:
demonstrate operational automation / SaaS logic beyond forms and screens.

### B4 — PROOF 3: PROFESSIONAL SYSTEM -> EVALUATION
Source:
professional-ai-agents.

Show:
candidate/qualification or failure->repair lifecycle at high level using real repository artifacts.

Purpose:
demonstrate that the same systems mindset extends into AI-agent engineering.

### B5 — PATTERN REVEAL / PAYOFF
Job:
make the shared logic explicit:
the visible outputs differ, but the work centers on relationships, rules, handoffs and verified behavior.

Do not:
turn the payoff into an unsupported personal-expertise claim.

## PROOF_PLAN

Strong evidence:
- real landing UI/request surface;
- real BayerCRM receiving/request surface or repo-backed flow diagram;
- real FleetDesk state screen/relationship;
- real professional-ai-agents issue/evaluation/library artifact.

Required:
at least one **observable transition/connection** per project family.

Weak/rejected:
- logos alone;
- static hero screenshots with no system relationship;
- generic code montage;
- AI imagery;
- unsupported before/after business results.

## MACRO_PACING

Use relative bands, not fixed seconds:

- 15–20% — common system question / attention contract;
- 20–25% — landing -> CRM proof;
- 20–25% — FleetDesk state-rule proof;
- 20–25% — AI-agent lifecycle/evaluation proof;
- 15–20% — pattern reveal / category payoff.

If comprehension suffers:
remove detail inside a proof block before removing the common pattern/payoff.

Do not accelerate technical labels so far that the operator audience cannot understand the relationship.

## VISUAL_COMMUNICATION_REQUIREMENTS

The asset must visually communicate **connections**, not just products.

Preferred recurring visual grammar:
`object/action -> rule/handoff -> next state/system`.

Examples at architecture level:
- landing request -> CRM;
- contract state -> vehicle state;
- candidate -> evaluation -> qualified/revise state.

This is a communication grammar, not final graphics direction.

Avoid one long uninterrupted FleetDesk screen recording in this launch asset.

## CREATOR_HANDOFF

### MUST_PRESERVE
- one common systems idea;
- three real proof families;
- proof before broad claim;
- no service list;
- no generic AI-expert posture;
- exact evidence scope;
- FleetDesk is one proof among several.

### BOUNDED
- exact hook language;
- degree of humor;
- project-order wording;
- how much implementation detail is spoken vs on-screen.

### MAY_CHOOSE
- authorial phrasing;
- metaphor if it does not distort the system;
- visual transition device;
- closing wording within the approved communication job.

### UNRESOLVED_NON_BLOCKING
- no conversion CTA approved;
- exact personal authorship wording remains constrained by brand-claim ledger;
- first-party channel performance history absent.

### MUST_ESCALATE
- any need to claim business impact;
- any claim that the user personally built every component;
- any attempt to replace proof with a generic services inventory;
- source asset that cannot safely/legibly show the verified relationship.
