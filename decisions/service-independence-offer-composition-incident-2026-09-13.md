# Service Independence / Offer Composition incident — 2026-09-13

decision_id: PBGS-PROF-GAP-006

status: ACTIVE / ROOT-CAUSE REPAIRED

affected_capability: Personal Brand Strategy -> Commercial Offer & Service Positioning

## Incident

The applied offer strategy converted the user's service set into a mandatory ladder:

`Website / Landing -> CRM -> Automation -> Custom System`.

That model then propagated downstream:
- audience language implied progression from landing into CRM;
- portfolio selected a landing-to-CRM asset as the first commercial proof;
- Content Architecture and Creative treated CRM depth as something the landing content should reveal.

User correction:
a client may legitimately want only a landing page. A CRM is not a required continuation of a landing. The same independence applies to CRM, automation and custom-system work.

## Root cause

**COMPOSITION MODEL ERROR inside the existing applied Commercial Offer & Service Positioning capability.**

The failure was not:
- missing Content Creative skill;
- missing Content Architecture skill;
- lack of technical evidence;
- need for a new professional core.

The strategy confused:
- **service adjacency / composability**
with
- **service dependency / mandatory sequence**.

## Agent Architect classification

**REPAIR EXISTING APPLIED CAPABILITY + DETERMINISTIC GOVERNANCE GATE**

No BUILD NEW.
No EXTEND upstream yet.

Reason:
the competence already belongs to offer/service positioning; the defect is a wrong judgment rule inside the applied specialization.

## Correct rule

Services may be:
- standalone;
- bundled;
- sequential;
- integrated;

depending on the actual buyer problem.

Never infer dependency merely because services can technically connect.

Current service modules:
- Website / Landing Page;
- CRM;
- Business Automation / Integrations;
- Custom Internal System / Custom CRM;
- optional AI capability where the buyer problem warrants it.

A buyer may purchase any one module without being pushed into the others.

## Content consequence

Brand breadth is established across the **content portfolio**, not by forcing multiple services into every artifact.

Allowed:
- one landing-only Reel;
- one CRM-only Reel;
- one automation-only Reel;
- one custom-system Reel;
- occasional integration Reel where integration itself is the real case.

Rejected default:
"show landing, then reveal CRM to prove depth."

## Regression cases

### SI-01 — landing-only buyer
Input:
buyer wants a standalone landing page.

Expected:
landing is treated as a complete legitimate service.
Do not add CRM/automation to the offer or content unless the problem requires it.

### SI-02 — CRM-only buyer
Input:
business already has acquisition channels and needs CRM/process work.

Expected:
CRM can be sold/explained independently.
Do not require a website project.

### SI-03 — automation-only buyer
Input:
existing tools need a repetitive handoff automated.

Expected:
automation can be scoped independently.

### SI-04 — genuine integrated case
Input:
real project explicitly connects landing -> CRM.

Expected:
integration may be shown as an integration case, but it must not redefine the general landing offer.

### SI-05 — portfolio breadth
Input:
brand has multiple service categories.

Expected:
breadth may be communicated across several assets.
Do not overload a single artifact merely to signal every capability.

## Upstream action

NO SEND.

Reopen only if repeated work shows the existing Personal Brand Strategy specialization cannot reliably distinguish standalone services from service composition.
